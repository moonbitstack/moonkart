moonbitstack/moonkart/concurrent

concurrent

The same cache behind an await, with loads coalesced per key.

Types and methods

fn[K : Eq + Hash, V] AsyncCache::get(Self[K, V], K) -> V?
An asynchronous handle around a cache. Loads are coalesced per key: while one task is computing a value for a key, other tasks asking for the same key wait for that computation instead of starting their own; tasks asking for other keys never wait on it. No lock is held while the loader runs. The only shared mutable state is the in-flight table, whose reads and writes are synchronous, so under the cooperative scheduler they never interleave. The first task to miss records a per-key Lazy, releases the scheduler by awaiting it, and the loader runs outside any shared critical section.

policy

Eviction policies. The cache sees them only through this contract, so a third-party policy plugs in without touching it.

Functions and values

fn new_lru(cap? : Int64, max_weight? : Int64) -> Lru
Creates an LRU policy. Set at most one of max_weight (evict by weight) or cap (evict by entry count).
fn new_s3fifo(cap? : Int64, max_weight? : Int64) -> S3Fifo
Creates an S3-FIFO-inspired second-chance FIFO. Bound by cap (entry count) or max_weight (total weight).
fn new_tinylfu(cap? : Int64, max_weight? : Int64, window_ratio? : Double, protected_ratio? : Double) -> Tinylfu
Creates a W-TinyLFU policy. window_ratio sizes the admission window; protected_ratio sizes the protected segment of the main region.
let tinylfu_protected_ratio : Double
Fraction of the main region given to the protected segment in W-TinyLFU. Entries read at least once are promoted here, away from the probation queue.
let tinylfu_window_ratio : Double
Fraction of capacity given to the admission window in W-TinyLFU. The window admits new entries before they must earn a place in the main region, so a burst of one-hit wonders does not evict the working set.

fn S3Fifo::admit(Self, Int64, Int64, Int32) -> Array[Int64]
S3-FIFO-inspired second-chance FIFO: a single FIFO queue with a visited bit per entry. When the queue is over budget, an entry that has been read since it entered is moved back to the tail with its bit cleared, while an entry never read since it entered is evicted. Scan floods and one-hit wonders are evicted on first sight, while repeated keys survive several rounds, at the cost of one boolean per entry.
